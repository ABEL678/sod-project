## 1. Резюме (TL;DR)

1. **Причина найдена.** Это не «забытый код», а зафиксированное решение Этапа 1 — правило
   «Плоская структура ПД/РД» в `docs/ARCHITECTURE.md` (стр. 151): все папки внутри суперпапок
   ИРД/ПД/РД создаются в едином скрытом разделе `COMMON`, «марка определяется по папке».
   Реальные объекты `Section` создаются только легаси-шаблоном `residential`, вручную через UI
   и демо-командой — поэтому в боевых проектах их нет.
2. **Рекомендация:** создавать базовые разделы-марки **в сервисном слое**, в точке
   `_populate_project_template` (вызывается из `create_project_from_template`), а **не через
   сигналы**. Сигналы неявны, срабатывают на каждом `Project.objects.create` (включая тесты),
   конфликтуют с веткой «восстановления из корзины» и ломают «гексагон лайт» (логика — в
   `services.py`).
3. **Миграций схемы НЕ требуется вообще**: `Section`, `Folder.section`, `Document.section`,
   `ProjectDocumentChunk.section` уже существуют. Нужны только: правки генератора структуры
   (~3 функции), новый идемпотентный сервис `_ensure_project_sections`, management-команда
   `sync_project_sections` для существующих проектов (перепривязка папок/документов/чанков
   от COMMON к маркам) и обновление тестов (баг закреплён тестом
   `test_project_templates.py:62` — `sections.count() == 0`).
4. **После фикса автоматически чинятся:** пустые списки в форме заданий (Этап 3), скрытая
   кнопка «Выдать задание» у ГИПа, попадание документов в COMMON, фильтр RAG по разделу
   (Этап 8), выдача `allowed_sections` смежникам, ГОСТ-шифры документов (сегмент «COMMON»
   исчезает). Этап 6 разблокирован без изменений в `task_summary_for_gip`.

## 3. Целевая модель

**Источник правды для «раздела» — объект `Section` (марка: АР, КР, КЖ, …). Папки марок внутри
суперпапок ПД/РД привязываются к своему `Section` (поле `Folder.section` уже есть).
`Document.section` наследуется от папки при загрузке. `COMMON` сужается до технического
контейнера ИРД и «нераспределённых» папок, из списков по-прежнему скрыт.**

- Разделы создаются **по шаблону проекта**: `PD_87` → 13 марок ПД; `RD_GOST` → 9 марок РД;
  `FULL` → объединение (13 + 6 = 19, дубли АР/КР/ТХ схлопываются по коду).
- Подразделы ИОС (ЭС, ВС, ВО, СС, ГС — «Раздел 5.x») **не** порождают отдельных разделов:
  папки подразделов остаются внутри дерева, но принадлежат разделу `ИОС`.
- ИРД остаётся в `COMMON` (исходные данные — не проектный раздел).
- Модель этапов жизненного цикла (WIP/SHARED/PUBLISHED/ARCHIVE) и `update_task_status` не затрагиваются.

### Отклонённые альтернативы

| Вариант | Почему отклонён |
|---|---|
| **Б. Оставить COMMON, марку деривировать из папки на лету** (`get_folder_mark_id`) | Не чинит главное: `Document.section` и `ProjectDocumentChunk.section` остаются COMMON → RAG-фильтр (Этап 8) и `allowed_sections` (M2M на `Section`) не работают |
| **В. Создавать разделы сигналом `post_save` на Project** | Неявность; срабатывает на каждом создании проекта (тесты, фиксации) до выбора шаблона; конфликт с веткой восстановления из корзины (`_restored_from_trash`); противоречит правилу «логика — в services.py» |
| **Г. Перенос данных через data-миграцию** | Перепривязка опирается на эвристики по именам папок; нужна возможность dry-run/повтора/отчёта. Management-команда наблюдаема, идемпотентна и запускается осознанно (в т.ч. после бэкапа) |

## 4. Пошаговые изменения (файлы и функции)

> Все шаги — один патч `sections-sync.patch`. **Миграций Django — ноль.**

### Шаг 1. Сервис создания разделов — `storage/domain/services.py`

**1.1. Новая функция `_ensure_project_sections(project, actor, template) -> dict[str, Section]`**

Идемпотентная (повторные вызовы — no-op), вызывается только из сервисного слоя:

- Строит список марок из `storage/domain/project_templates.py`:
  `template.get('pd')` → `PD_SECTIONS`, `template.get('rd')` → `RD_SECTIONS`;
  дедупликация по коду марки (первое вхождение — ПД, порядок: ПД по номерам, затем
  недостающие РД).
- Для каждой марки: `Section.objects.get_or_create(project=project, code=mark, defaults=…)`
  с `name` (правило D3, §6) и `full_code = generate_gost_code(project.base_code, mark)`
  (`services.py:992`), `order` — сквозной порядковый номер.
- COMMON не создаёт (им занимаются `_get_or_create_common_section` и ИРД-ветка).
- `Section.folder_template` не заполняет (легаси-поле, вне рамок фикса).

**1.2. Правка `_populate_project_template` (`services.py:862-873`)**

После `_ensure_root_superfolders(...)` добавить:

```
sections = _ensure_project_sections(project, actor, template)
```

и передать словарь `sections` в `_create_pd_structure` / `_create_rd_structure`.

**1.3. Правка `_create_pd_structure` (`services.py:771-828`)**

- Папка раздела ПД (`section_folder`) и её «Часть 1 …» / подразделы создаются с
  `section=sections.get(mark, common)` вместо `common`.
- Подразделы 5.x — с `section=sections['ИОС']`.
- Fallback на `common` сохраняется (если марки нет в словаре — защита от рассинхрона).

**1.4. Правка `_create_rd_structure` (`services.py:830-859`)**

- Папка марки и «Комплект 1» создаются с `section=sections.get(mark, common)`.

**1.5. `_create_ird_structure` (`services.py:740-768`) — не меняется** (ИРД в COMMON).

**1.6. `create_project_from_template` (`services.py:4053-4130`) — без структурных правок**

- Ветка `residential` (строки 4096-4122) сохраняет текущее поведение (создаёт свои 4 раздела).
- Ветка `template is None` (строки 4125-4127): разделы не создаются (проект без шаблона) —
  решение D5, §6: такие проекты добиваются командой `sync_project_sections`.
- Ветка восстановления из корзины (`_restored_from_trash`, 4089-4092) — без изменений;
  недостающие разделы для восстановленных проектов также добивает команда.

**1.7. `reset_project_structure` (`services.py:877-925`) — самоподхват**

Удаляет все `Section` (стр. 904) и разворачивает шаблон заново — после Шагов 1.1-1.4 разделы
марок пересоздаются автоматически. Проверить тест, который считает `created_sections`.

### Шаг 2. Команда переноса данных — `storage/management/commands/sync_project_sections.py`

Новая команда `manage.py sync_project_sections` (по образцу существующего
`backfill_profiles.py`). Флаги: `--project <code>` (один проект; без флага — все активные),
`--dry-run` (печатает план, ничего не пишет), `--default-marks RD` (для проектов с пустым
`template_key`, решение D5).

**Алгоритм (на каждый проект, в `transaction.atomic`):**

1. **Определить шаблон:** `project.template_key` → `PROJECT_TEMPLATES`; пусто/неизвестно →
   берётся `--default-marks` (по умолчанию — не создавать, только отчёт).
2. **Создать недостающие разделы:** вызов `_ensure_project_sections(project, system_actor, template)`
   (actor нужен только для совместимости сигнатуры; у `Section` нет `created_by`).
3. **Перепривязать папки марок** (сейчас `folder.section = COMMON`) по правилам:
   - строим карту «имя папки → марка» из `PD_SECTIONS` / `RD_SECTIONS` выбранного шаблона
     (нормализация: `strip`, схлопывание пробелов, регистр — как в шаблоне);
   - **дерево РД:** папка верхнего уровня внутри суперпапки «РД» с именем из `RD_SECTIONS`
     → `section = Section(mark)`; все её потомки (комплекты, вложенные папки) наследуют
     тот же раздел;
   - **дерево ПД:** папка верхнего уровня с именем из `PD_SECTIONS` → свой раздел;
     дочерние папки («Часть 1 …», подразделы 5.x, их «Часть 1 …») → раздел родителя
     (подразделы ИОС → `ИОС`);
   - **дерево ИРД и системные папки этапов жизненного цикла** — не трогаются (остаются COMMON/None);
   - папки, имя которых не совпало ни с одним шаблонным именем (переименованные
     пользователем, «Прочие…») — **остаются в COMMON**, попадают в отчёт «не сопоставлено»;
   - сопоставление строго по совпадению имени; по коду не матчим (у папок марок код пуст).
4. **Перенести документы:** для каждой перепривязанной ветки:
   `Document.objects.filter(folder__in=ветка, is_deleted=False).update(section=раздел)`;
   документы без папки и документы в несопоставленных папках остаются в COMMON.
5. **Обновить RAG-чанки:** `ProjectDocumentChunk.objects.filter(document__in=…).update(section=раздел)`.
   **Переиндексация не нужна** — вектор не пересчитывается, меняется только метаданные-снимок;
   `chunk.folder` не меняется.
6. **Пересчитать шифры:** `_refresh_project_full_codes(project)` (`services.py:1133`) —
   заполнит `Section.full_code` и актуализирует `Folder.full_code` (коды папок при этом
   не меняются: у папок марок код пустой, у «Часть 1/Комплект» коды вида `2345-АР1`
   уже содержат марку).
7. **Отчёт в stdout:** создано разделов N; перепривязано папок M (списком по маркам);
   перенесено документов K; обновлено чанков C; не сопоставлено папок U (имена).
   Второй запуск — все счётчики, кроме п.1-2, нулевые (идемпотентность).

**Безопасность:** бэкап БД перед запуском обязателен (deploy/backup.sh); откат — из бэкапа
(структура изменений точечная: `section_id` у 4 таблиц).
