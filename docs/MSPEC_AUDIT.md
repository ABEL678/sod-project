## 2. Особые проверки (обязательные)

### 2.1. Волна 0, п.1 — ВСЕ места хранения состояния документа и кто их пишет/читает

Состояние документа хранится **не в одном, а в четырёх хранимых полях плюс вычисляемая зона**. Именно это — главный конфликт плана с кодом.

| # | Поле | Где объявлено | Значения |
|---|---|---|---|
| 1 | `Document.status` | models.py:118-124 | draft / in_review / approved / archived |
| 2 | `Document.suitability_code` | models.py:149-154 (choices 128-137) | S0-S4, A, B, CR |
| 3 | `Document.internal_status` | models.py:161-166 (choices 155-160) | draft / internal_review / rework / ready_to_share |
| 4 | `Folder.zone` (зона папки, в которой лежит документ) | models.py:294-299 (choices 252-257) | WIP / SHARED / PUBLISHED / ARCHIVE |
| — | «Эффективная зона» | services.py:2873-2878 `_effective_zone` | вычисляется: каноническая папка зоны → её zone, иначе по status (ZONE_BY_STATUS, services.py:2686) |

Карты соответствия: ZONE_STATUS_MAP (services.py:87-92: WIP→draft, SHARED→in_review, PUBLISHED→approved, ARCHIVE→archived), ZONE_SUITABILITY_MAP (services.py:94-99: WIP→S0, SHARED→S3, PUBLISHED/ARCHIVE→A).

**Кто пишет:**
1. `update_document_status` (services.py:2852-2870) — status + suitability_code; единственная точка смены статуса с FSM-валидацией.
2. `update_internal_status` (services.py:2980-3028) — internal_status; при уходе из draft синхронно гасит status в draft (3021-3025).
3. `transition_document_zone` (services.py:3136-3207) — папка + status + suitability_code + internal_status (rework при возврате, 3198-3199); единственная точка контролируемого перехода зон.
4. `upload_document` (services.py:3303-3519) — при создании документа ставит status/suitability по зоне папки (3421-3428), при загрузке новой версии в другую папку переводит статус с FSM-проверкой (3441-3477), обновляет `current_version` (3496-3498).
5. `move_document` (services.py:1868-1907) — статус/пригодность по целевой канонической зоне; смена зоны через DnD запрещена (1788-1812), перевод в PUBLISHED при открытых замечаниях запрещён (1882-1894).
6. `copy_document` (services.py:2010-2017) — копия получает status/suitability целевой папки.
7. Прямые сохранения: страж `Document.save()` (models.py:205-243) перехватывает изменения status/suitability_code вне сервисов и прогоняет `validate_transition` — но **не** перехватывает internal_status и folder.
8. Django-admin: status/suitability_code у Document readonly (storage/admin.py:31-36), т.е. админка не может менять их напрямую.

**Кто читает:**
- Права и FSM: `can_transition` (services.py:2735-2815), `_workflow_role_allowed` (2909-2935), `check_zone_permission` (2469+).
- Интерфейс: `_document_row` (services.py:154-183), `get_project_documents_queryset` (572+), `get_zone_counts` (3223-3242), панель действий `document_actions` (3069-3109); визуальные зоны/сегмент-контрол (views.py:637+, `_get_active_zone`).
- ИИ-контур: индексация версии по `current_version` (services.py:3504-3517), DocumentVersion.indexing_status (models.py:366-371).
- Фильтры и виды: DOCUMENT_VIEW_FILTERS (services.py:79-82: status, suitability_code, internal_status).

**Конфликт с планом:** пункт «одно главное состояние, прочее вычисляется» против 4 хранимых полей + 3 карт соответствия. Дополнительно: `SUITABILITY_CHOICES` содержит и 'A' «Утверждён», и 'CR' «Утверждён» (models.py:134-136) — два кода с одинаковым русским названием (CR — исполнительная документация). Волна 0 п.1 обязана решить судьбу suitability_code и CR, иначе «одно состояние» не получится. Объём **L** (миграция данных + все 7 точек записи + фильтры/виды + экспорты).

### 2.2. Волна 0, п.3 — где хранятся Project.gip и Membership.role, кто пишет, что мигрировать

**Хранение (два места, синхронизации между ними в коде НЕТ):**
- `Project.gip` — FK на User, SET_NULL (models.py:43).
- `ProjectMembership.role_in_project` — CharField с choices (models.py:419-439); 'gip' — валидная роль участника.
- Плюс третья, «компанийская» роль: `UserProfile.role` (models.py:392-402) — именно её читают все проверки прав (services.py:2730-2732 `_user_role`, 2752), включая FSM.

**Кто пишет Project.gip:**
1. `create_project` (services.py:1133 — восстановление из корзины, 1161 — создание); `_validate_gip_role` (702-708): ГИПом может стать только UserProfile.role ∈ {gip, admin} или superuser.
2. `update_project` (services.py:1299-1306).
3. Django-admin ProjectAdmin (admin.py:17-21 — gip в списке; форма редактирования открыта).
4. `create_project_from_template` (services.py:4131+) — через create_project (внешний API POST /api/v1/projects/ передаёт gip=request.user — external_api/views.py:66-75).

**Кто пишет Membership.role_in_project:**
1. `update_project_member_role` (services.py:675-699): запрет снять роль последнего ГИП, если project.gip пуст (690-695); при выдаче 'gip' — `_validate_gip_role` (687-688).
2. `add_company_member` (services.py:4226+).
3. Django-admin ProjectMembershipAdmin (admin.py:52-55).

**Кто читает (обоих источника):**
- `_is_project_gip` (services.py:2900-2906): `project.gip_id == user.id` **ИЛИ** membership с role='gip' — двойной источник прямо в проверке.
- `can_manage_project_participants` (444+), права на действия над проектом (can_edit/can_archive_project 1179-1195).
- UI: project_detail/participants, edit_member.html, таблицы.

**Рассинхрон возможен:** update_project меняет только project.gip (1299-1306) и не трогает membership; update_project_member_role меняет только membership и не трогает project.gip (675-699) — единственная связка — проверка «последний ГИП» (690-695). Т.е. сегодня может быть: project.gip=X, а в составе роль gip у Y, либо project.gip=X при отсутствии X в составе вообще.

**Что мигрировать под план (ГИП = вычисляемое из состава):**
1. Данные: для каждого проекта, где project.gip не NULL и нет membership с role='gip' — создать membership (или проставить роль). Правило разрешения дублей (несколько 'gip' в составе) план не задаёт — код сегодня позволяет несколько memberships с 'gip' (уникальность только project+user, models.py:434).
2. Код: убрать поле Project.gip (миграция), все writers → на membership; `_is_project_gip` → только по membership; сериализация S3 (mapping.py) и external_api — поля gip нет в выгрузке заданий, но в `serialize_section`/metadata gip не передаётся (проверено: export.py:103-129 — gip в metadata отсутствует); UI карточки проекта — вычисляемое значение.
3. Rиски: admin.py:19 (list_display), тесты, демо-команда create_demo_project.
Объём **M**. Замечание: план говорит «точка ввода роли — одна», но роль уже вводится в двух точках (UserProfile при добавлении в компанию — add_company_member 4226+; роль в проекте — update_project_member_role 675+ / admin). Это надо развести явно в редакции плана (см. [ПРЕДЛОЖЕНИЕ] в части 2).

### 2.4. Раздел 2 — фактические шифры и имена файлов в generate_gost_code и project_templates.py против раздела 4.2 ГОСТ Р 21.101-2026

**Фактическая логика шифров в коде:**
- `generate_gost_code(base, section, *folders)` (services.py:1068-1082) — простая склейка непустых частей через дефис. Без проверки состава/символов/порядка по 4.2.
- `Section.full_code = base_code-марка` (services.py:787-790); `Folder.full_code` — цепочка кодов (services.py:1426-1470, `_folder_full_code`).
- Шифр документа при загрузке: `_generate_document_code` (services.py:3272-3300) = `[base_code]-[section.code]-[folder.code]-[NN]`, NN двузначный с перебором коллизий (3297-3299); при пустом префиксе — 'DOC-' (3291).
- Коды комплектных папок создаёт шаблонизатор:
  - ПД, часть раздела: `{base}-` + `{марка}1` (services.py:890), для ИОС — `{base}-ИОС1.{n}` (876-879), где `base-` — `_code_prefix` (735-737).
  - РД, комплект марки: `{base}-` + `{марка}1` (services.py:932).

**Конкретные расхождения:**

1. **Дублирование базового обозначения в шифре документа** — для документов в комплектных папках шаблона. Пример: project.base_code='2345-12', марка АР → папка РД-комплекта получает code='2345-12-АР1' (services.py:932) → шифр документа в ней = '2345-12-АР-2345-12-АР1-01' (services.py:3286-3290 склеивает base, section.code И folder.code). Базовое обозначение входит в шифр дважды; структура не соответствует правилам обозначений (базовое обозначение — марка — номер комплекта/листа, без повторов). Аналогично для ПД-частей (876-890) и для ИОС-частей '2345-12-АР-2345-12-ИОС1.1-01'. Это не косметика: шифр документа уникален в (project, section, code) (models.py:193) и печатается в документах.
2. **ПД-шаблон: отсутствует раздел «ПОД» и сдвинута нумерация разделов 8-13** — project_templates.py:61-198 содержит 13 разделов: 8=ООС, 9=ПБ, 10=ТБЭ, 11=ОДИ, 12=СМ, 13=ИД. В известной мне действующей редакции ПП №87 (после Изм. 2019 г.) разделов 14: между ПОС и ООС добавлен «Проект организации работ по сносу или демонтажу объекта капитального строительства» (8=ПОД, 9=ООС, 10=ПБ, 11=ТБЭ, 12=ОДИ, 13=СМ, 14=ИД). Ограничение: текст ред. ПП №87 от 21.10.2025 у меня отсутствует — сверить нумерацию по официальному тексту, но факт «в шаблоне 13 разделов и нет раздела о сносе/демонтаже» из кода зафиксирован точно.
3. **Подразделы ИОС 5.1-5.6** (ЭС, ВС, ВО, ОВ, СС, ГС — project_templates.py:93-136) — совпадают с действующей структурой раздела 5 ПП №87. Совпадение.
4. **РД-марки: подмножество таблицы марок** — project_templates.py:200-218: АР, КР, КЖ, КМ, ОВ, ВК, ЭОМ, СПА, СС, АК, ТХ (11 марок). Типовых марок (ГП, ГЧ, ЭО, НВК, ТС и др.) нет; пользовательские разделы создаются свободно (create_section services.py:1389-1419, Section.code — произвольная строка до 20, models.py:70) — т.е. справочник марок не привязан к таблице В.1 ГОСТ и не валидируется. Для 25-человек компании это осознанное подмножество, но в плане «марки по таблице В.1» — нужна фиксация «разрешённые марки» где-то в системе, а не только в шаблоне.
