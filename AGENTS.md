## Ограничения (Архитектура и код)

### Архитектура
- **Домен чистый.** `storage/domain/` не зависит от Django views, почтовых задач и т.д.
- **Порты и адаптеры.** Всё внешнее (хранение файлов, почта, ИИ) — через интерфейсы в `ports/`.
- **Бизнес-логика — только в `domain/services.py`**. Views вызывают сервисы, а не пишут логику сами.
- **`upload_document()`** — единственная точка создания версий документа.

### Backend (Django)
- Не создавай `DocumentVersion` напрямую во views или почтовых задачах. Только через `services.upload_document()`.
- Не меняй модели из `docs/ARCHITECTURE.md` без обновления этого файла.
- Не добавляй Celery, Redis, pgvector, пока явно не попросят (см. MASTER_SPEC).

### Общее
- **Не добавляй новые зависимости** без согласования.
- **Не переписывай архитектуру** без согласования.
- **Не оставляй `print(...)`** в коде (используй `logging`).
- **Не оставляй `TODO`** без задачи в `MASTER_SPEC.md`.

## Порядок работы с репозиторием
1. Агент не пушит в origin. Готовит коммиты в локальной ветке,
   в отчёте указывает имя ветки и хеш коммита.
2. Пуш в origin выполняет только владелец, напрямую в main, без PR.
3. CI запускается на push в main. Прогонов на PR нет.
4. Полные серийные прогоны тестов запрещены — нигде и никогда.
   Локальная проверка: только затронутые приложения,
   python manage.py test <приложения> --parallel 4 --verbosity=1.
5. Базовые замеры времени «до/после» не снимаются; если нужна
   оценка — брать из отчётов CI на почте.
6. Полный suite в CI: один параллельный прогон (--parallel 4)
   на каждый push в main; ожидать его вручную не нужно,
   результат приходит на почту.
7. Ветки после вливания в main удаляются (git branch -d),
   живые неслитые ветки не трогать без согласования с владельцем.

## Три роли (координатор — аудитор — управляющий)

| Роль | Кто | Что делает |
|---|---|---|
| **Координатор** | Kilo (Code) | Ведёт подсессию, пишет код, коммитит (с разрешения человека) |
| **Аудитор** | Kilo (Суб-агент auditor, DeepSeek V4.1) | Проверяет план/код по чек-листу, выносит APPROVE / CHANGES REQUIRED |
| **Управляющий** | Человек | Задаёт правила, решает архитектурные споры |

**Правила:**
- Координатор **не** аудирует сам себя — аудит делает отдельный суб-агент.
- Аудитор **не** меняет код. Только отчёт.
- Коммит — только после `APPROVE` аудитора и с разрешения человека.

## Процедура аудита и проверки (уровень волны)

1. Аудит кода выполняет внешний аудитор (chat.z.ai) по команде
   владельца. Исполнитель кода аудит не запускает и не назначает.
2. Исполнитель может выполнить самопроверку второй сессией, но:
   - называет её строго «самопроверка второй сессией»;
   - НЕ использует слова «аудит» и «APPROVE» в отчётах;
   - результат указывает фактом: «найдено/не найдено», с перечнем.
3. Полный аудит волны — строго после пуша её последнего шага.
   Аудитору отдаётся вся волна (диапазон коммитов от первого до
   последнего), не отдельный коммит.
4. Промпт для аудитора готовит владелец (совместно с оркестратором),
   не исполнитель. В промпте всегда указываются: адрес репозитория,
   диапазон коммитов и фокусные направления проверки.
5. Волновой аудит считается завершённым только когда пришёл вердикт
   (BLOCKER/MAJOR/MINOR/INFO по каждому направлению). Следующий шаг
   после завершения волны не пушится до вердикта.
6. Правила-константы (в действии до переноса в иные доки):
   - все команды — через .venv\Scripts\python.exe; ModuleNotFoundError
     на пакете из requirements.txt — признак неверного интерпретатора;
   - PostgreSQL для тестов — контейнер sod-db-dev (порт 5433),
     при необходимости docker start sod-db-dev, отметить в отчёте;
   - полные и серийные прогоны не запускаются, локально — только
     затронутые модули, --parallel 4;
   - замеры времени не снимать; подсчёт ORM-запросов через
     assertNumQueries / CaptureQueriesContext разрешён и является
     тестовым артефактом, а не замером времени;
   - пуш не выполняется никогда, только владелец.
