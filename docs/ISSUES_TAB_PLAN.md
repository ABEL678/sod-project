### 2.2. Что подтверждает диагноз Координатора

1. Замечания создаются только из документа (`issues/urls.py:13`, `documents/<int:document_id>/issues/create/`) и просматриваются в вьювере/на странице реестра, вход на которую — только dropdown `_topbar.html`. Со страницы проекта (главного рабочего экрана) до них не добраться.
2. Единой выборки «все замечания проекта» как сервиса нет: есть приватные
   `_registry_*`-функции вьюхи. Существующие сервисные функции (`get_issues_for_version`,
   `services.py:3752`) — пер-документные, не пер-проектные.
3. Связи замечания с `DesignTask`/`RfiTask` **не существует ни в каком виде**:
   `Issue` связан только с `Document` (`issues/models.py:19`). «Замечание блокирует
   задачу» сегодня нигде не фиксируется и не отображается.

### 2.3. Ограничения, которые надо учесть

- `Issue.document` — обязательный FK: замечание без документа невозможно,
  выборка всегда идёт через права на документы (`_registry_issues`). Вкладка
  обязана наследовать эту семантику прав (не показывать замечания по документам,
  которые пользователь не может читать).
- Дублирование логики фильтров недопустимо: реестр, вкладка и экспорт должны
  фильтровать одинаково — отсюда перенос в сервисный слой.
- R2 (вкладка RFI) в работе: план не должен конфликтовать с ней. Вкладка
  «Замечания» вставляется после «Задания»; вкладка RFI (когда выйдет) — между
  «Задания» и «Замечания» (точка решения §6.1).

## 3. Целевая модель

### 3.1. Вкладка «Замечания» (пункт 1 задачи)

Структура панели (по образцу вкладки «Задания», `project_detail.html:476`):

```
{% elif active_tab == 'issues' %}
  toolbar:      «Замечания проекта» · badge N · [Excel] (ссылка на существующий export)
  Сводка:       6 карточек (§3.2)
  чипы-группы:  zone-segment — Открытые / В работе / На проверке / Закрытые /
                Просрочено / Блокируют работу (клик → flag=…)
  фильтры:      Статус · Автор (новый) · Ответственный · Документ (новый) · Поиск
  таблица:      № · Документ · Раздел · Текст · Автор · Ответственный · Срок ·
                Статус · Блокирует (бейджи З-12 / РИ-3)
  пагинация:    50 на страницу (как реестр)
```

Решения:

1. **Механика фильтров** — HTMX-паттерн реестра (`hx-get` на
   `?tab=issues`, `hx-target="#issuesPanel"`, `hx-push-url`): фильтры применяются
   мгновенно, состояние в URL — это соответствует UX-решению, принятому в реестре
   и ИИ-вкладках (prуф: `registry.html:85-94`).
2. **Шаблон** — новый партиал `issues/templates/issues/_issues_panel.html`
   (извлечение общей части реестра). Реестр-страница (`registry.html`) и вкладка
   включают один и тот же партиал; различаются только заголовком/URL-базой.
   Так «Открытые» и колонки не разъедутся между экранами (симметрия с
   `ISSUE_STATUS_GROUPS`, закомментированная в `issues/views.py:356-357`).
3. **Доступ** — вкладка добавляется в `allowed_tabs` для всех участников
   (`storage/adapters/views.py:830-834`), как «Задания»: исполнитель должен видеть
   замечания по документам, которые он читает. Видимость строк — через
   `project_issues(user, project)` (права на документы, §2.3).
4. **Пустое состояние** — «Замечаний нет. Замечания создаются в вьювере
   документа: откройте документ и отметьте место на листе» (создание замечания
   вне документа не проектируем — FK обязательный, это осознанное ограничение модели).

### 3.2. Сводка по замечаниям (пункт 2 задачи)

Карточки в шапке вкладки (по образцу `task_dashboard.html:40-56`):

| Карточка | Считается от | Переход (клик) |
|---|---|---|
| Всего | все видимые | `?tab=issues` |
| Открытые | `NEW + REJECTED + DISCUSSION` (группа `open`) | `?tab=issues&flag=active` |
| В работе | `IN_PROGRESS` (группа `progress`) | `?tab=issues&flag=progress` |
| На проверке | `DONE` (группа `review`) | `?tab=issues&status=DONE` |
| Просрочено | `due_date < today` AND статус ∈ `ACTIVE_ISSUE_STATUSES` — красная подсветка при >0 | `?tab=issues&flag=overdue` |
| Блокируют работу | замечания, у которых `blocked_design_tasks` или `blocked_rfi_tasks` непусты (активные) | `?tab=issues&flag=blocking` |

Секция «Требуют внимания» (под карточками, сворачиваемая; по образцу таблицы
`dashboard-attention` из Сводки заданий): просроченные; `NEW` без исполнителя;
активные `REJECTED`. Колонка «Причина» с бейджем — так же, как в Сводке заданий
(`task_dashboard.html:84-96`).

Отдельная страница Сводки по замечаниям **не строится**: вкладка уже даёт
карточки + внимание-таблицу + полный реестр. Страница реестра
(`/projects/<id>/issues/`) сохраняется без изменений как deep-link (топбар,
ссылки из карточек реестра). API Сводки для ГИП-Ассистента (`issues_summary`)
— вне этого плана, точка решения §6.6.

### 3.3. Сервисный слой (пункт 3 задачи)

Ответ на вопрос Координатора: **новая выборка нужна, но не с нуля** — логика
существует в приватных функциях вьюхи реестра. Переносим в сервисный модуль
`issues/services.py` (приложение `issues` сейчас не имеет сервисного модуля —
есть `notify.py`; «гексагон лайт» для storage живёт в `storage/domain/services.py`,
но `Issue` — модель приложения `issues`, и её сервисы держим рядом с ней, как
`notify.py`).

| Функция (новый модуль) | Была | Изменения |
|---|---|---|
| `project_issues(user, project)` | `_registry_issues` (`views.py:384`) | без изменений логики; публичная |
| `apply_issue_filters(qs, params)` | `_apply_registry_filters` (`views.py:396`) | + фильтр `author` (по pk или `me`); + фильтр `document` (по pk, select_related для колонки); + `flag=blocking` (§3.4) |
| `issue_summary(user, project)` | `_registry_context_counts` (`views.py:432`) | + счётчики по каждой группе отдельно (`open`, `progress`, `review`, `closed`), + `blocking` |
| `issues_requiring_attention(user, project)` | нет (новая) | по образцу `tasks_requiring_attention` (`services.py:5374`): просроченные + NEW без исполнителя + активные REJECTED; возвращает список декорированных строк с `reason_label`/`reason_badge` |
| `blocking_links_map(user, project)` | нет (новая) | для таблицы вкладки: одним запросом собрать по всем замечаниям проекта их связанные задания/RFI (PK, номер, тип), чтобы избежать N+1 в колонке «Блокирует» |

Вьюхи делегируют: `IssueRegistryView`, `IssueRegistryExportView` вызывают
сервисы вместо приватных функций (приватные имена оставляем как тонкие
обёртки на один релиз — не ломая ничего внешнего, они не используются
вне `issues/views.py`).

Новые фильтры `author`/`document` немедленно работают во всех трёх потребителях
(реестр, вкладка, Excel) — потому что фильтрация одна.

### 3.4. Связь с DesignTask и RFI: блокировка (пункт 4 задачи)

#### 3.4.1. Модель

Две M2M-связи на `Issue` (миграция `issues/0008_issue_blocking_links.py`,
последняя миграция issues — `0007_issue_external_id`):

```python
blocked_design_tasks = models.ManyToManyField(
    'storage.DesignTask', blank=True, related_name='blocking_issues',
    verbose_name="Блокирует задания")
blocked_rfi_tasks = models.ManyToManyField(
    'storage.RfiTask', blank=True, related_name='blocking_issues',
    verbose_name="Блокирует RFI")
```

Отклонённые альтернативы:
- FK `blocking_issue` на DesignTask/RfiTask (N:1) — не покрывает «одно замечание
  блокирует несколько задач» (типичный случай: замечание по ИРД-документу
  блокирует целую группу заданий смежников).
- Вычислять эвристикой «замечания по документам, связанным с задачей» —
  недостоверно, у DesignTask нет жёсткой связи с входными документами (только
  `DesignTaskAttachment` на выход).

Симметрия чтения: со стороны задания — `task.blocking_issues.all()` (свежие
M2M с related_name), со стороны замечания — `issue.blocked_design_tasks.all()`.

#### 3.4.2. Кто и как устанавливает связь

- В **карточке замечания** (`issue_detail_htmx`, `issues/views.py:283` — панель
  HTMX): секция «Блокирует» со списком связанных заданий/RFI и кнопкой
  «+ Задание / + RFI» — выбор из заданий/RFI проекта (список ограничен
  доступными пользователю: для заданий — существующая выборка `list_tasks`,
  для RFI — `rfi_tasks` проекта). Связь снимается крестиком.
- В **карточке задания** (`task_detail`) и в будущей карточке RFI — только
  отображение (read-only бейдж-строка «Блокировано замечаниями: N») со
  ссылками на замечания. Управление связями — из карточки замечания (одна
  точка правки, чтобы не размывать права).
- Права на установку связи: автор замечания, ответственный замечания,
  ГИП/админ проекта — совпадает с правами смены статуса замечания
  (`IssueUpdateStatusView`).

#### 3.4.3. Отображение в интерфейсе

| Экран | Что появляется |
|---|---|
| Вкладка «Замечания» | колонка «Блокирует»: бейджи «З-12» (задание, ссылка) и «РИ-3» (RFI, ссылка); чип-фильтр «Блокируют работу» |
| Карточка замечания | секция «Блокирует» + управление |
| Карточка задания (`task_detail`) | предупреждение «Заблокировано замечаниями: N» (красный бейдж при активных замечаниях, серый — если все замечания закрыты/аннулированы) |
| Вкладка «Задания» (`project_detail` `?tab=tasks`) | мини-бейдж замечаний в строке задания (кол-во активных блокирующих) |
| Сводка заданий (`task_dashboard`) | новая причина в таблице «Требуют внимания»: задача с ≥1 активным блокирующим замечанием попадает в список с `reason_label = «Блокировано замечанием»` (расширение `tasks_requiring_attention`, `services.py:5374`) |
| Вкладка RFI (R2) | тот же бейдж — координация с командой R2 (в RFI_MODULE_PLAN.md секция UI уже спроектирована; добавка — одна колонка) |

#### 3.4.4. Правила статусов (осознанные границы MVP)

- Связи **не блокируют переходы** статусов заданий/RFI автоматически: закрыть
  задание с активными замечаниями технически можно — система лишь
  предупреждает бейджем (точка решения §6.5: возможный запрет в будущем).
- «Активное» блокирующее замечание = статус ∈ `ACTIVE_ISSUE_STATUSES`
  (`NEW`, `IN_PROGRESS`, `REJECTED`, `DISCUSSION`); закрытые/аннулированные
  замечания не считаются блокирующими, но остаются в истории связей.
- `task_summary_for_gip`/`rfi_summary_for_gip` в MVP не меняем; счётчик
  «blocked» добавляется в `issue_summary` (§3.3) и опционально в Сводку
  заданий (§3.4.3, причина в attention-таблице).

## 4. Пошаговые изменения (файлы и функции)

Кодер реализует следующее (перечень, не код):

### Шаг 1. Сервисный слой — новый `issues/services.py`

- Перенести из `issues/views.py`: `project_issues` (бывш. `_registry_issues`),
  `apply_issue_filters` (бывш. `_apply_registry_filters`), `issue_summary`
  (бывш. `_registry_context_counts`), константы `ISSUE_STATUS_GROUPS`/
  `ACTIVE_ISSUE_STATUSES` (остаются экспортируемыми из старого места через
  импорт для совместимости).
- Новое: `issues_requiring_attention(user, project)`, `blocking_links_map(user, project)`,
  новые фильтры `author` / `document` / `flag=blocking` в `apply_issue_filters`.
- Вьюхи `IssueRegistryView`, `IssueRegistryExportView` — вызывают сервисы.
- Видимость: по-прежнему через `get_readable_documents` — никаких новых прав.

### Шаг 2. Модель и миграция — `issues/models.py`, `issues/migrations/0008_issue_blocking_links.py`

- Два M2M-поля на `Issue` (`blocked_design_tasks`, `blocked_rfi_tasks`,
  `related_name='blocking_issues'`, `blank=True`).
- Миграция только с добавлением полей (без data-миграций: существующие
  замечания ничего не блокируют по умолчанию).

## 6. Точки решения для Координатора

1. **Порядок вкладок.** Рекомендация: «Документы · Задания · RFI (R2) ·
   Замечания · Участники · Корзина · ИИ-вкладки». Сейчас (до R2) «Замечания»
   встаёт сразу после «Задания».
2. **Карточки Сводки в вкладке vs отдельная страница.** Рекомендация: карточки
   в вкладке, отдельную страницу не строить (реестр уже несёт сводку; дублировать
   экраны не нужно). Если Координатор хочет полный аналог страницы Сводки
   заданий — механика карточек переносится 1:1, но это +1 шаблон и +1 URL.
3. **M2M vs FK для блокировок.** Рекомендация: M2M на `Issue` (§3.4.1).
4. **Управление связями только из карточки замечания.** Рекомендация: да
   (одна точка правки, ясные права). Если нужно «из задания тоже» — добавить
   симметричный блок в task_detail (небольшая доработка шага 5).
5. **Блокирующие замечания запрещают закрытие задания?** Рекомендация: нет,
   только предупреждение (не усложнять статусную машину заданий в MVP).
6. **API Сводки для замечаний** (`issues_summary` для ГИП-Ассистента/S3) —
   вне этого плана; сделать после приёмки вкладки (симметрично
   `rfi_summary_for_gip`, `services.py:5910`).
7. **Фильтр «документ»** — select всех читаемых документов проекта (может быть
   большим) или поле поиска по коду. Рекомендация: select с ограничением
   (только документы, у которых есть замечания) + поле `q` покрывает остальное.
