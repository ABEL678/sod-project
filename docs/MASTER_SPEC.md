# MASTER_SPEC.md — СОД для проектной компании

**Версия:** 1.2
**Дата:** 2026-10-29
**Статус:** Живой документ. Обновляется по мере прохождения этапов.

## 1. Цель продукта

Дать небольшой проектной компании (25 человек) порядок в проектных файлах: актуальные версии, понятные права, быстрый поиск. Убрать «файлы в мессенджерах» и «а вот та самая версия». В перспективе — автоматизировать рутину (почта, ведомости, замечания) и дать ИИ-агенту доступ к знаниям проекта. Интеграция с экосистемой (ГИП-Ассистент, ВОР-билдер, Витро-трекер).

## 2. Пользователи и роли

| Роль | Что делает | Что видит |
|---|---|---|
| **Администратор** | Управляет пользователями, проектами, правами | Всё |
| **ГИП** | Ведет проект, утверждает документы, ставит замечания | Всё в своих проектах |
| **Инженер** | Загружает чертежи в свои разделы, читает смежные | Свои разделы — запись, остальные — чтение |
| **Наблюдатель** | Смотрит, не меняет | Только чтение |
| **Смежник (contractor)** | Читает выданные разделы, загружает свои | Только разрешенные разделы |

## 3. Функциональные требования (по этапам)

### Этап 1. Ядро: проекты, разделы, документы, версии (ЗАВЕРШЕН)
- Создание проекта, разделов, загрузка документов с версионированием.
- Права: инженер — пишет в разрешенные, наблюдатель — читает.
- Админка Django.

### Этап 2. Автоматизация структуры папок (ЗАВЕРШЕН)
- Модель FolderTemplate, создание папок на диске при создании проекта.

### Этап 3. Ведомости документов с гиперссылками (ЗАВЕРШЕН)
- Страница «Ведомость», экспорт в Excel с ссылками на текущую версию.

### Этап 4. Замечания и исходные данные (ЗАВЕРШЕН)
- Модель Issue, страница документа с вкладкой «Замечания», «Мои замечания».
- Исходные данные (source_data) — загружает только ГИП/админ.

### Этап 5. Аутентификация (ЗАВЕРШЕН)
- Вход/выход, защита страниц.

### Этап 6. Поиск и навигация по ревизиям (ЗАВЕРШЕН)
- Глобальный поиск по проекту, быстрый переход к версии, «Последние документы».

### Этап 7. GUI-улучшения по мотивам Vitro-CAD / Sarex (ЗАВЕРШЕН)
- Виды таблицы (DocumentView), счётчики разделов, вкладка «Участники» с управлением ролями.
- Ограничения: без PDF-вьювера и пинов (это Этап 8).

### Этап 8. PDF-вьюер и визуальные замечания (пин) — СЛЕДУЮЩИЙ
**Цель:** замечание «прибито» к месту на чертеже, как в Vitro-CAD / Sarex.
- PDF.js на странице версии.
- Поля в Issue: page_number, x_ratio, y_ratio.
- Создание замечания кликом по PDF, отображение пинов, переход «замечание → PDF» и «PDF → замечание».
- **Критерий готовности:** инженер ставит замечание на узле, ГИП видит пин в том же месте.

### Этап 9. Карточка замечания 2.0 (обсуждение, сроки, реестр)
**Цель:** полноценный инструмент коммуникации.
- Модели: IssueComment, IssueAttachment.
- Поля в Issue: assignee, due_date.
- «Мои замечания» с фильтрами (просроченные, открытые).
- Счётчик замечаний в дереве разделов.
- Экспорт реестра замечаний в Excel.

### Этап 10. Экспорт PDF с наложенными замечаниями (PyMuPDF)
**Цель:** «печатная» версия чертежа с пинами и списком замечаний.
- Генерация PDF через PyMuPDF (fitz).

### Этап 11. Интеграция с экосистемой (API Gateway) — НОВЫЙ
**Цель:** СОД выступает центральным хабом для ГИП-Ассистента, ВОР-билдера и Витро-трекера.
- Создание порта `ExternalIntegrationPort`.
- Django-приложение `external_api` с REST-эндпоинтами.
- Аутентификация по API-ключам (привязка к Company).
- Контракты API:
  - `POST /api/v1/projects/` (ГИП-Ассистент)
  - `GET /api/v1/projects/{code}/specifications/` (ВОР-билдер)
  - `POST /api/v1/projects/{code}/vor/` (ВОР-билдер)
  - `POST /api/v1/projects/{code}/issues/sync/` (Витро-трекер)
  - `GET /api/v1/projects/{code}/issues/pending/` (Витро-трекер)
- **Критерий готовности:** ВОР-билдер может забрать СО и отдать ВОР через API СОД.

## 4. Нефункциональные требования

| Требование | Значение |
|---|---|
| Пользователей одновременно | до 25 |
| Объем хранилища | до 500 ГБ (локально или S3) |
| Время отклика списка документов | < 1 сек |
| Резервное копирование | ежедневно, БД + media/ (cron + rsync) |
| Аутентификация | Django-сессии, пароли через set_password |
| Развертывание | один сервер (VPS или локальный), Docker по желанию |
| Резервный доступ | админка Django всегда доступна админу |

## 5. Ограничения и допущения

- **Не делаем** мобильное приложение, интеграцию с CAD на старте.
- **Не делаем** микросервисы, Celery, Redis, pgvector, пока не пройден этап 8.
- **Не делаем** тонкие права на уровне отдельных документов — только разделы и проекты.
- **Предполагаем**, что пользователи работают через браузер на десктопе.
- **Предполагаем**, что файлы загружаются вручную или из почты.

## 6. Порядок работ и контрольные точки

| Этап | Что делаем | Контрольная точка |
|---|---|---|
| 1 | Ядро: модели, сервисы, views, права | ГИП создает проект, инженер грузит 2 версии, наблюдатель скачивает |
| 2 | Автосоздание папок | Новый проект → папки на диске |
| 3 | Ведомости + Excel | Ведомость с рабочими ссылками в браузере и Excel |
| 4 | Замечания + исходные данные | Замечание создано, увидено, закрыто |
| 5 | Аутентификация | Вход/выход работает |
| Деплой | PostgreSQL, Nginx, Gunicorn, домен | Система доступна по HTTPS |
| 6 | Поиск и навигация по ревизиям | Документ и версия находятся за 1-2 действия |
| 7 | GUI-улучшения | Вид таблицы сохраняется; участники работают |
| 8 | PDF-вьюер и пины | Замечание видно на PDF в том же месте |
| 9 | Карточка замечания 2.0 | Обсуждение, сроки, экспорт работают |
| 10 | Экспорт PDF с замечаниями | PDF с пинами скачивается |
| 11 | Интеграция с экосистемой | ВОР-билдер забирает СО через API |

**Правило:** не начинаем следующий этап, пока не пройдена контрольная точка текущего.
