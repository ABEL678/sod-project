## 3. Ответ на вопрос Координатора 2 (dict-ячейка, дубли счётчиков)

**dict-ячейка вместо NamedTuple — следствие для M3 подтверждено.** Разрешение переменных в шаблонах Django: `{{ cell.status }}` на dict резолвится как `cell['status']` (порядок lookup: словарь → атрибут → индекс) — шаблонный код M3 идентичен для dict и NamedTuple, включая `{% if cell.status == 'DONE' %}`. Оговорка зеркальна З2 СТОП-1: в **python-коде** вьюхи/тестов доступ только `cell['status']` (`cell.status` на dict — AttributeError). Требование к M3: в шаблонах — без разницы; в вьюхе `_get_matrix_context` и в тестах — только ключевой доступ.

**Дубли `total`/`non_cancelled` и сверх-счётчики `returned`/`on_hold`/`review` — оставить, это не «лишнее», а зафиксированный дизайн §3.2:**
- `non_cancelled` хранится отдельным служебным полем «т.к. правило 1 сравнивает `done == non_cancelled`» (план :119); `total` — отображаемый счётчик К3 (У4-а: не-CANCELLED, план :115/:224).
- `returned`/`on_hold`/`review` — «счётчики для правил 3/4/5» (план :120), служебные.
- Обоснование плана :122: служебные поля нужны, «чтобы статус ячейки вычислялся из тех же данных, что легли в базу, и были перепроверяемы тестами без БД» — то есть M2-тесты обязаны уметь вызвать `compute_cell_status(cell)` и сверить с `cell['status']`; без этих ключей замыкание «счётчики → статус» на живых данных недостижимо.
- Цена хранения — до 9 int на ячейку × ~900 ячеек при 30 разделах (Р1, план :291) — ничтожна; это память запроса, не БД и не новый запрос.
- Пожелание (не требование): в сервисе маркировать служебные ключи комментарием («не для шаблона»), чтобы M3 случайно не вынес их в UI — отображаемых счётчиков ровно 4 из К3 (§3.2 :122, чек-лист :323).
- `COUNTER_KEYS` (+14 строк в `tasks_matrix.py`) без текста дифа не верифицируема — гипотеза: множество 7 Ф3-ключей как единый источник имён для сборки dict в сервисе (защита от опечаток ключей). Проверка — часть 2.
