## 1. Резюме (TL;DR)

Матрица заданий — решётка N×N по разделам проекта (источник × цель), где ячейка пары (source_section, target_section) показывает агрегированный статус и четыре честных счётчика по существующим `DesignTask`. Данные уже есть: у каждого задания не-null FK-пара с PROTECT (`models.py:732–743`) и составной индекс `(project, source_section, target_section, …)` (`models.py:806–814`) — агрегация ляжет на готовый индекс. Оси — разделы проекта (`Section`, unique `(project, code)`, `models.py:82`) без COMMON (прецедент: `services.py:550–551`, `views.py:1390–1395`). Ничего из этого в коде не существует: ни одного QuerySet с группировкой по парам нет (аудит §5.1).

Состав работ: чистая функция статуса ячейки (без БД, стиль `mapping.py`) + один ORM-запрос агрегации + вкладка `?tab=matrix` в `ProjectDetailView` + drill-down в существующий список заданий через новый фильтр пары (прецедент `?task_section`, `views.py:1200–1204`). Цепочка статусов ячейки — 7 состояний, приоритеты зафиксированы Координатором (К1); три формализации ниже (§3.4) закрывают дыры полноты цепочки, не меняя её сути.

### 1.1. Принятые решения Координатора (фиксируются как есть)

| № | Решение | Статус |
|---|---|---|
| К1 | Цепочка приоритетов статуса ячейки (первое совпадение решает): 1) DONE — все не-CANCELLED задачи пары в {COMPLETED, ACCEPTED}; 2) OVERDUE — ≥1 с due_date < сегодня в статусах {DRAFT, ISSUED, IN_PROGRESS, ON_HOLD, RETURNED}; 3) REWORK — ≥1 RETURNED; 4) WAITING_INFO — ≥1 ON_HOLD; 5) REVIEW — ≥1 REVIEW; 6) IN_PROGRESS — ≥1 IN_PROGRESS; 7) NOT_STARTED — остальные (все в {DRAFT, ISSUED}). Просрочка гасится статусами {COMPLETED, ACCEPTED, REVIEW, CANCELLED}: сдал на проверку — работа сделана. Отличия от ГИП-Ассистента: OVERDUE выше REWORK (осознанно); REVIEW — явный статус ячейки (их баг «REVIEW проваливается в NOT_STARTED» не повторяем); WAITING_INFO оживлён — у нас он означает ON_HOLD («жду ИД»), у них мёртвый enum (`enums.py:26–33`, ветки возврата нет — аудит §5.2.2) | Принято |

| К3 | Ячейка несёт статус + честные счётчики **полями** (не текстовой строкой, как у них `matrix_service.py:92–94` + регэксп `MatrixCell.tsx:23–28`): всего / в работе / просрочено / завершено | Принято |

### 1.2. Формализации Аудитора (не оспаривают К1, закрывают полноту цепочки)

| № | Формализация | Обоснование |
|---|---|---|
| Ф1 | Правило 1 читается как: `не-CANCELLED-задач в паре > 0` И `все они в {COMPLETED, ACCEPTED}`. Пара, где все задачи CANCELLED, — **не** DONE (исключаем вакуумную истинность «все не-CANCELLED в {}»): падает в правило 7 → NOT_STARTED | Иначе пара «всё отменено» загорится зелёным «готово» — противоречит семантике DONE; граничный случай «пара без задач после CANCELLED» прямо требует покрытия тестами (ТЗ, §6) |
| Ф2 | Правило 7 — это fallback: «NOT_STARTED — если ни одно из правил 1–6 не сработало». Пояснение в скобках «(все в {DRAFT, ISSUED})» — типовой случай; смесь DRAFT+CANCELLED (и любые сочетания с CANCELLED вне правила 1) тоже падает в fallback | К1 перечисляет 7 правил как «первое совпадение решает» — fallback обязан быть тотальным, иначе цепочка не полна (сочетание DRAFT+CANCELLED не покрыто ни одним правилом в букве К1) |
| Ф3 | Состав счётчиков К3: «всего» = не-CANCELLED задачи пары (универсум матрицы — тот же, что у правила DONE); «в работе» = IN_PROGRESS; «просрочено» = задачи с `due_date < today` в статусах {DRAFT, ISSUED, IN_PROGRESS, ON_HOLD, RETURNED} (тот же предикат, что правило 2 — счётчик и статус считаются одним фильтром и не могут разойтись); «завершено» = COMPLETED+ACCEPTED. Отменённые задачи не попадают ни в один счётчик (согласовано с Ф1/Ф2) | Состав в К3 не задан; вариант «всего = все задачи» вынесен на решение У4 (§5). Совпадение предикатов просрочки исключает класс рассинхрона «статус OVERDUE, а счётчик просрочено = 0» |

### 3.2. Вход/выход сервиса

Вход: `project` (обязательный), `today` (опциональный; None → `timezone.localdate()`, прецедент `services.py:5358`; параметр — для детерминизма тестов).

Выход — словарь:

```
{
  'sections': [Section, …],            # оси, уже отсортированы (order, code), COMMON исключён
  'cells': {(src_id, tgt_id): cell},   # только пары, где есть хотя бы одна задача
  'today': date,
}
```

Ячейка (`cell`) — NamedTuple с полями (К3 + служебные для вычисления статуса):

| Поле | Состав | В шаблон |
|---|---|---|
| `source_section_id`, `target_section_id` | — | ключ связи с осями |
| `status` | результат `compute_cell_status` (7 значений, §3.4) | да |
| `total` | не-CANCELLED задачи пары (Ф3; альтернатива — У4) | да |
| `in_progress` | статус IN_PROGRESS | да |
| `overdue` | `due_date < today` И статус в {DRAFT, ISSUED, IN_PROGRESS, ON_HOLD, RETURNED} (тот же предикат, что правило 2 К1) | да |
| `done` | статусы {COMPLETED, ACCEPTED} | да |
| `non_cancelled` | = `total` по Ф3; хранится отдельным полем, т.к. правило 1 сравнивает `done == non_cancelled` | нет (служебное) |
| `returned`, `on_hold`, `review` | счётчики для правил 3/4/5 | нет (служебные) |

Отображаемые счётчики — ровно четыре из К3; служебные поля нужны, чтобы статус ячейки вычислялся из тех же данных, что легли в базу, и были перепроверяемы тестами без БД.

### 3.3. ORM-часть (один запрос агрегации)

Два запроса на вызов, оба прецедентированы:

1. Оси: `Section.objects.filter(project=project).exclude(code='COMMON').order_by('order', 'code')` — соединение прецедентов `services.py:550–551` (exclude) и `services.py:312` (order_by).
2. Агрегация: `DesignTask.objects.filter(project=project).values('source_section_id', 'target_section_id').annotate(...)` — условные `Count` по статусам (составы — как в таблице выше); образец условной аннотации в модуле: `task_summary_for_gip` (`services.py:5360–5361` — values+annotate) и `get_sections_with_counts` (`services.py:552–556` — `Count(..., filter=Q(...))`).
3. Сtatus каждой ячейки — `compute_cell_status(counters)` из чистого модуля; в сервисе — только вызов, никакой статечной логики.

### 3.4. Чистая функция статуса ячейки (формализация К1)

Вход — счётчики из §3.2; выход — одна из 7 строк: DONE / OVERDUE / REWORK / WAITING_INFO / REVIEW / IN_PROGRESS / NOT_STARTED. Порядок ветвления = приоритет К1, первое совпадение решает:

1. `non_cancelled == 0` → NOT_STARTED (Ф1: «всё отменено»/пустая пара — не DONE);
2. `done == non_cancelled` → DONE (К1-1 в записи через счётчики; все не-CANCELLED в {COMPLETED, ACCEPTED});
3. `overdue >= 1` → OVERDUE (К1-2);
4. `returned >= 1` → REWORK (К1-3);
5. `on_hold >= 1` → WAITING_INFO (К1-4);
6. `review >= 1` → REVIEW (К1-5);
7. `in_progress >= 1` → IN_PROGRESS (К1-6);
8. иначе → NOT_STARTED (К1-7 как fallback, Ф2).

Свойства: тотальность (любое сочетание статусов даёт ровно один результат), детерминизм, независимость от БД/времени (время входит только в предикат просрочки на ORM-уровне). Для сравнения — эталон ГИП-Ассистента: 5 правил без fallback-полности (`matrix_service.py:138–169`), REVIEW не покрыт, REWORK-ветка падает в рантайме (`:158–159`, `enums.py:26–33`) — оба дефекта не наследуются.

### 3.5. Сложность запросов: аннотации vs Python-группировка

| Вариант | Стоимость | Оценка |
|---|---|---|
| **А. Аннотации (выбран)** | 1 GROUP BY-запрос по `(source_section_id, target_section_id)` с фильтром `project`; условные Count в одной аннотации; строк в ответе ≤ числа фактических пар | GROUP BY идёт по префиксу готового индекса `design_task_proj_src_tgt_idx` (`models.py:806–814`: project, source_section, target_section, …) — сканирование по индексу, без сортировок. Память O(пар). Прецедент условной аннотации — `services.py:552–556` |
| Б. Python-группировка (`list_tasks('all')` + цикл) | загрузка всех задач проекта в память с 6 join'ами select_related (`services.py:5472–5477`), O(задач) объектов; для проекта с тысячами задач — ощутимо; плюс дублируется логика гейта | уместна там, где список всё равно нужен (вкладка, drill-down) — но не для самой матрицы |

Вывод: агрегация — аннотациями (вариант А); Python-группировка остаётся только в drill-down, где она уже прецедентирована (`views.py:1200–1204`) и список задач пары действительно нужен построчно. Объём задач проекта не ограничивает выбор: А линейнее по памяти и опирается на индекс.

### 6.1. Чистые функции, без БД (`SimpleTestCase`, прецедент `test_error_pages.py:6`)

Файл: `storage/tests/test_tasks_matrix.py`. Класс `ComputeCellStatusTests` (импорт `storage.domain.tasks_matrix` — модуль без Django-моделей, как `mapping.py`):

- частичное завершение: COMPLETED + DRAFT (без прочих признаков) → NOT_STARTED, `done == 1` (счётчики честные);
- граничные: одна задача в паре; все счётчики нули.

Класс `TasksMatrixForProjectTests`:

- пустой проект: оси пустые/только разделы, `cells` пусто — решётка рендерится без ошибок;
