# MASTER_SPEC.md — СОД для проектной компании

**Версия:** 1.1
**Дата:** 2026-10-28
**Статус:** Живой документ. Обновляется по мере прохождения этапов.

## 1. Цель продукта

Дать небольшой проектной компании (25 человек) порядок в проектных файлах: актуальные версии, понятные права, быстрый поиск. Убрать «файлы в мессенджерах» и «а вот та самая версия». В перспективе — автоматизировать рутину (почта, ведомости, замечания) и дать ИИ-агенту доступ к знаниям проекта.

## 2. Пользователи и роли

| Роль | Что делает | Что видит |
|---|---|---|
| **Администратор** | Управляет пользователями, проектами, правами | Всё |
| **ГИП** | Ведет проект, утверждает документы, ставит замечания | Всё в своих проектах |
| **Инженер** | Загружает чертежи в свои разделы, читает смежные | Свои разделы — запись, остальные — чтение |
| **Наблюдатель** | Смотрит, не меняет | Только чтение |
| **Смежник (contractor)** | Читает выданные разделы, загружает свои | Только разрешенные разделы |

## 3. Функциональные требования (по этапам)

### Этап 1. Ядро: проекты, разделы, документы, версии

**Цель:** работающая система, где можно создать проект, разделы и загружать файлы с историей версий.

**Требования:**
- Создание проекта (шифр, название, заказчик, ГИП).
- Создание разделов внутри проекта (АР, КР, ОВ, ВК и т.д.) с порядком сортировки.
- Загрузка документа: шифр, название, тип (drawing, source_data, report, other), файл, комментарий.
- Автоматическое версионирование: повторная загрузка с тем же шифром в тот же раздел создает новую версию, старая сохраняется.
- Просмотр списка документов с текущей версией и историей.
- Скачивание любой версии.
- Разграничение прав: инженер пишет только в разрешенные разделы, наблюдатель — только читает.
- Админка Django для управления пользователями и ролями.

**Критерий готовности:** ГИП создает проект, инженер загружает чертёж, повторно загружает новую версию, наблюдатель видит обе версии и скачивает нужную.

### Этап 2. Автоматизация структуры папок

**Цель:** при создании проекта папки на диске создаются сами, по шаблону.

**Требования:**
- Модель FolderTemplate (имя шаблона, список папок).
- При создании Project и Section — автоматическое создание папок через порт FileStorage.
- Возможность редактировать шаблон в админке.
- Обработка ошибок: если папка уже существует — не падать.

**Критерий готовности:** создали проект «ЖК-2026-01» — на диске появились media/projects/ЖК-2026-01/АР/, /КР/ и т.д.

### Этап 3. Ведомости документов с гиперссылками

**Цель:** ГИП нажимает кнопку и получает ведомость, где каждая строка — ссылка на актуальный файл.

**Требования:**
- Страница «Ведомость» по проекту (и по разделу).
- Таблица: шифр, название, тип, текущая версия, дата, автор, статус, ссылка на скачивание.
- Экспорт в Excel (.xlsx) с гиперссылками (openpyxl).
- Сортировка по разделу и шифру.

**Критерий готовности:** ведомость открывается в браузере, ссылки кликабельны, Excel-файл скачивается и открывается с рабочими гиперссылками.

### Этап 4. Замечания и исходные данные

**Цель:** замечания живут рядом с документом, исходные данные — отдельный тип с особыми правами.

**Требования:**
- Модель Issue: проект, раздел, документ (опционально), версия (опционально), автор, адресат, описание, статус (open, in_progress, closed), даты.
- Страница документа: вкладка «Замечания» с формой создания и списком.
- Личный кабинет: «Мои замечания» (где я адресат).
- Исходные данные: doc_type='source_data', загружать может только ГИП или админ, читают все участники проекта.
- Уведомления (внутри системы, без email на этом этапе): колокольчик с новыми замечаниями.

**Критерий готовности:** инженер создает замечание к версии чертежа, ГИП видит его в «Моих замечаниях», закрывает, инженер видит статус «Закрыто».

### Этап 5. Аутентификация (ЗАВЕРШЕН)

**Цель:** Вход/выход, защита страниц от анонимов.
(Реализовано в рамках MVP. Требования: стандартная Django-авторизация, Login/Logout views).

### Этап 6. Поиск и навигация по ревизиям (приоритет: боль пользователя №1)

**Цель:** пользователь находит нужный документ и нужную версию за 1–2 действия, а не листает дерево разделов.

**Требования:**
- **Глобальный поиск по проекту** (строка поиска в шапке Explorer):
  - Поиск по Document.code, Document.name, DocumentVersion.comment.
  - Фильтры: раздел, тип документа (doc_type), статус, диапазон дат загрузки версии.
  - Результат — список документов с указанием: текущая версия, дата, автор, ссылка «открыть документ» и «история версий».
- **Быстрый переход к конкретной версии:**
  - На странице документа — выпадающий список версий с датой и комментарием; выбор версии сразу открывает скачивание/просмотр этой версии.
  - В результатах поиска — прямая ссылка на нужную версию (не только на документ).
- **Поиск по замечаниям** (минимально): поиск по тексту Issue.description с фильтром по проекту.
- **«Мои недавние»**: на главной странице проекта — блок «Последние 10 документов, которые я открывал/скачивал» (хранится в сессии, без новых таблиц).

**Ограничения:**
- Не внедрять Elasticsearch/Whoosh/Solr. Поиск — через icontains / Q-объекты. Индексируем только метаданные.
- Полнотекстовый поиск по содержимому PDF/DOCX — не в этом этапе (это Этап 10).

**Критерий готовности:** инженер вводит «АР-01» в поиск, видит нужный документ, выбирает версию 3 из выпадающего списка и скачивает её — без перехода по дереву разделов.

### Этап 7. GUI-улучшения по мотивам Vitro-CAD / Sarex

**Цель:** довести интерфейс до «на ощупь как у больших», не добавляя тяжёлых зависимостей.

**Требования:**
- **Переключаемые виды таблицы документов** (сохраняемые наборы столбцов/фильтров/сортировки):
  - Личные виды и общие (для всех участников проекта).
  - Хранить в отдельной лёгкой модели DocumentView (JSON-поле с настройками).
- **Счётчик файлов у разделов** в левом дереве: «АР (12)».
- **Карточка участников проекта**: вкладка «Участники» на странице проекта.
- **Кликабельные ссылки в Excel-ведомости**: в каждой строке — ссылка на текущую версию и ссылка на страницу истории версий.
- **Сводка замечаний при скачивании** (опционально, чекбокс): при скачивании PDF можно приложить .txt со списком Issue.

**Ограничения:**
- Не делать PDF-viewer и пин-аннотации в этом этапе (это Этап 8).
- Не добавлять фронтенд-фреймворки (React/Vue).

**Критерий готовности:** инженер настраивает свой вид таблицы, сохраняет его, перезаходит — вид сохранился; ГИП открывает вкладку «Участники» и видит роли всех участников проекта.

### Этап 8. Визуальные замечания на PDF (пин) — после деплоя

**Цель:** замечание «прибито» к месту на чертеже, как в Vitro-CAD / Sarex.
**Статус:** запланировано, но не начинать до деплоя и сбора обратной связи.

**Требования:**
- PDF-viewer на странице версии (PDF.js).
- Поля в Issue: page_number (int, null), x_ratio (float, null), y_ratio (float, null).
- Создание замечания кликом по PDF; отображение пинов; переход «замечание → PDF» и «PDF → замечание».

**Критерий готовности:** инженер ставит замечание на конкретном узле чертежа, ГИП открывает PDF и видит пин в том же месте.

### Этап 9. Интеграция с почтой (ОТЛОЖЕН)

(Сохранены исходные требования из версии 1.0)
**Требования:**
- Модель MailRule: ящик (IMAP), фильтр (отправитель, тема, тело), целевой проект, целевой раздел, doc_type.
- Фоновая задача (management-команда по cron): подключается к IMAP, ищет письма по правилам, скачивает вложения, вызывает upload_document().
- Лог обработки: какие письма обработаны, какие вложения созданы.
- Ручной запуск из админки для теста.
- Защита: не обрабатывать одно и то же письмо дважды (флаг processed в БД).

**Критерий готовности:** письмо от заказчика с вложением .pdf и темой «ЖК-2026-01 Исходные данные» автоматически создает документ в разделе «ИД» проекта «ЖК-2026-01».

### Этап 10. ИИ-поиск и MCP-сервер (ОТЛОЖЕН)

(Сохранены исходные требования из версии 1.0)
**Требования:**
- Извлечение текста из DocumentVersion (PDF, DOCX, TXT) при загрузке.
- Векторизация текста и хранение эмбеддингов (pgvector или отдельная таблица).
- Семантический поиск по проекту: запрос → список документов с релевантными фрагментами.
- MCP-сервер: инструменты search_documents(query, project_id), get_document_text(doc_id), list_issues(project_id), get_vedomost(project_id).
- Доступ агента только к разрешенным проектам (проверка прав по API-ключу пользователя).

**Критерий готовности:** агент через MCP находит документ по смыслу запроса и возвращает ссылку на актуальную версию.

## 4. Нефункциональные требования

| Требование | Значение |
|---|---|
| Пользователей одновременно | до 25 |
| Объем хранилища | до 500 ГБ (локально или S3) |
| Время отклика списка документов | < 1 сек |
| Резервное копирование | ежедневно, БД + media/ (cron + rsync) |
| Аутентификация | Django-сессии, пароли через set_password |
| Развертывание | один сервер (VPS или локальный), Docker по желанию |
| Резервный доступ | админка Django всегда доступна админу |

## 5. Ограничения и допущения

- **Не делаем** мобильное приложение, публичный API, интеграцию с CAD на старте.
- **Не делаем** микросервисы, Celery, Redis, pgvector, пока не пройден этап 4.
- **Не делаем** тонкие права на уровне отдельных документов — только разделы и проекты.
- **Предполагаем**, что пользователи работают через браузер на десктопе.
- **Предполагаем**, что файлы загружаются вручную или из почты, а не сохраняются напрямую из CAD.

## 6. Порядок работ и контрольные точки

| Этап | Что делаем | Контрольная точка |
|---|---|---|
| 1 | Ядро: модели, сервисы, views, права | ГИП создает проект, инженер грузит 2 версии, наблюдатель скачивает |
| 2 | Автосоздание папок | Новый проект → папки на диске |
| 3 | Ведомости + Excel | Ведомость с рабочими ссылками в браузере и Excel |
| 4 | Замечания + исходные данные | Замечание создано, увидено, закрыто |
| 5 | Аутентификация | Вход/выход работает |
| Деплой | PostgreSQL, Nginx, Gunicorn, домен | Система доступна по HTTPS |
| 6 | Поиск и навигация по ревизиям | Документ и версия находятся за 1-2 действия |
| 7 | GUI-улучшения | Вид таблицы сохраняется; участники работают |
| 8 | Визуальные замечания (пин) | Замечание видно на PDF в том же месте |
| 9 | Интеграция с почтой | Письмо → документ в нужном разделе |
| 10 | ИИ-поиск + MCP | Агент находит документ по смыслу |

**Правило:** не начинаем следующий этап, пока не пройдена контрольная точка текущего.

## 7. Правила для ИИ-агента Kilo

При генерации кода обязательно:
1. Читать ARCHITECTURE.md и MASTER_SPEC.md перед каждой задачей.
2. Работать строго в рамках текущего этапа. Не забегать вперед.
3. Не менять модели и контракты сервисов без обновления ARCHITECTURE.md.
4. Не добавлять зависимости, не указанные в текущем этапе.
5. После генерации — показывать diff и список измененных файлов.
