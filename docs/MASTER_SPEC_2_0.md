Stream-CAD — единая точка сборки и единый источник правды по проекту: исходные данные, задания, замечания, версии документов, шаблоны и регламентные формы живут здесь, а не в сетевой папке, Excel и мессенджере. Принцип: сначала ежедневная выгода проектировщику, дисциплина — на её фоне.

## 2. Нормативный фундамент

Всё, что платформа генерирует и проверяет, строится на действующих нормах, без самодельных бланков:

- ГОСТ Р 21.101-2026 — правила оформления проектной и рабочей документации: формы основных надписей (3, 4, 6), единая табличная форма ведомостей (форма 2), марки основных комплектов (таблица В.1), правила обозначений и шифров (раздел 4.2), состав общих данных (4.3.1), разрешение на внесение изменений (раздел 7, приложение Л: формы 9 и 9а, коды причин по таблице Л.1).
- Постановление Правительства РФ № 87 (ред. от 21.10.2025, действует до 01.09.2028) — состав разделов ПРОЕКТНОЙ документации стадии «П». Состав рабочей документации этим постановлением не задаётся — опора: марки и составы основных комплектов РД по ГОСТ Р 21.101-2026 и задание на проектирование.
- Сущность «стадия» проекта («П», «РД»; далее по необходимости): от стадии зависит, каким нормативом определяется состав документации. «П» — ПП № 87, «РД» — ГОСТ Р 21.101-2026.
- Внутренние стандарты организации — надстройкой над нормативом.
- Отдельная задача в составе волны 1: сверить генераторы и шаблоны с редакцией 2026 года (правила имён файлов электронных документов, марки основных комплектов). Аудитом зафиксированы конкретные расхождения:
  1. двойное базовое обозначение в шифре документа — устранение перенесено в волну 0, п. 9 (решение владельца: это дефект текущей выдачи, а не предмет сверки);
  2. ПД-шаблон содержит 13 разделов (project_templates.py:138-198). Проверено по действующей редакции ПП № 87 (ред. 21.10.2025): обязательный перечень — 13 разделов, отдельного раздела о сносе/демонтаже нет — с 01.09.2022 он входит в состав раздела 7 «Проект организации строительства». Шаблон соответствует действующей редакции; замечание аудита о «ПОД» снято;
  3. правило имён файлов электронных документов в коде отсутствует полностью: файлы сохраняются с именем пользователя (services.py:3486-3493), при скачивании имя = шифр документа (views.py:4795-4798); копирование документов СОД→СОД отсутствует (решение владельца 27.11.2026 — см. волну 0, п. 7);

## 4. Волна 1 — ежедневная ценность проектировщика

**4.1. Учёт исходных данных** — первый пункт волны. Карточка выдачи/приёмки: кто выдал, что именно, какая версия, кому передано в работу, когда. Версии исходных данных рождаются вне платформы — она их регистрирует. Ответ на запрос на информацию принимается системной кнопкой «Принять как исходные данные» с автосвязью с запросом — цепочка «спросил → получил → зафиксировал → передал смежникам» прослеживается целиком. С активацией реестра в волне 1 включается тип причины версии «исходные данные» (волна 0, п. 5). Аудит: RFI-модуль готов почти целиком (модель RfiTask models.py:950-1023, переходы services.py:5831-5913, папка ИРД/RFI services.py:5916-5970), но register_rfi_response (services.py:5884-5894) только привязывает документ-ответ — версии не создаёт и «принято как ИД» не фиксирует; кнопка 4.1 достраивает ровно этот шаг. Почтовый импорт: в коде есть MailRule (models.py:480-497) и только симуляция импорта из почты (views.py:4897-4924); реального IMAP-импорта нет. Решение владельца: почтовый импорт ИД в первой рабочей версии не делается — осознанный отказ; файлы исходных данных загружаются вручную. MailRule остаётся в коде для маршрутизации типов. Пересмотр по данным пилота: если исходные данные в основном приходят письмами — почтовый импорт возвращается в план как резервный канал карточки приёмки.

**4.2. Шаблоны и генераторы по формам ГОСТ.** Титульные листы, ведомости (форма 2), состав проекта, листы общих данных. Спецификация — источник, ВОР — производный документ (строка ВОР знает, из какой строки спецификации выросла); модели не сливаются. Каждый сгенерированный документ несёт в служебных данных версию шаблона и редакцию норматива, по которым выпущен. Владелец каталога шаблонов — ГИП (решение владельца). Аудит-факты, на которые опирается пункт: форм ГОСТ не существует в коде (перечень имеющихся генераторов — MSPEC_AUDIT.md п. 2.5: ведомость xlsx произвольного вида views.py:4821-4894, матрица заданий xlsx/pdf views.py:2334-2670, реестры); строки Specification (models.py:553-586) и VorItem (models.py:588-620) не связаны — у VorItem нет ссылки на строку спецификации, «знает, из чего вырос» сегодня невыполнимо; шаблоны — кортежи в коде (project_templates.py:12-218), версионирования нет. Обязательные шаги волны: (а) связь VorItem.specification (FK, миграция); (б) устранение двойного базового обозначения в шифре документа (раздел 2, задача сверки); (в) фиксация «разрешённых марок» по таблице В.1 с валидацией при создании раздела (сейчас Section.code — произвольная строка, services.py:1389-1419).

**4.3. Обсуждения по любой сущности.** Комментарии переходов статусов остаются протоколом решений и не смешиваются с обсуждением. Видимость сообщений — по ролям, флаг видимости ставится на сообщении. Смена статуса при открытом обсуждении требует закреплённой резолюции (краткий итог с решением). Параллельно — договор о каналах внутри организации: юридически значимые ответы — только в платформе; мессенджер — для бытовых вопросов. Аудит: обсуждения есть только у замечаний (IssueComment issues/models.py:99-123); протокол смены статуса документа отсутствует как текст — update_document_status (services.py:2852-2870) не принимает комментарий вовсе (в отличие от заданий: update_task_status с обязательным комментарием services.py:5118-5174). **4.4. Поиск с ответами по документам.** Не «ИИ ответит», а «покажу, где в ваших документах об этом сказано». Аудит: каркас уже реализован — чанки версий и история с источниками (ai_checks/domain/models.py:187-305), вьюхи поиска и истории (ai_checks/views.py:97-350), автоиндексация PDF-версий при загрузке (services.py:3504-3517); контур выключен флагом AI_CHECKS_ENABLED=False (sod_core/settings.py:118). Остаток волны: включение на проде, контроль объёмов индексации — не новая разработка.

**4.5. Метрики волны 1** (фиксируются до запуска): доля заданий, заведённых в платформе (а не в мессенджере); время от вопроса до первого ответа в обсуждении; доля пользователей с повторными рабочими сессиями за неделю. ## 5. Волна 2 — дисциплина и регламент

**5.1. Простые проверки, встроенные в шаги процесса.** Фиксированный набор детерминированных проверок в момент перехода: комплектность комплекта по составу общих данных (4.3.1), заполненность основной надписи по формам 3/4/6, правильность имён файлов; связность спецификации, ВОР и листов на уровне ссылок. У каждой проверки — владелец и порядок отключения/уточнения. Там, где автопроверка ненадёжна (штамп зависит от разбора файлов), — человеческий чек-лист с блокирующими пунктами как запасной путь. При добавлении новой проверки — обратная проверка архива отчётом, без блокировки. Содержательная проверка текста — позже, с ИИ. Аудит-факт: ИИ-нормоконтроль СПДС выведен из эксплуатации — модели RuleDefinition/CheckRun/PendingCheckResult/ReminderRule удалены (ai_checks/domain/models.py:9-11, миграция ai_checks/migrations/0013) — волна 2 стартует с нуля, движка «правил» в коде больше нет (что соответствует отказу раздела 9). Детерминированные валидации, которые уже вызываются в шагах и остаются как база: FSM и T70-блокировки (перечень точек — MSPEC_AUDIT.md п. 2.6), валидация загрузки (расширение/размер services.py:3337-3352), матрицы заданий/RFI с обязательными комментариями (services.py:5097-5122, 5831-5913). Для «человеческого чек-листа» точка опоры уже есть — DesignTaskChecklistItem (models.py:915-947): переиспользовать модель чек-листа задания как основу чек-листа проверки, а не создавать параллельную сущность. Решение владельца: не восстанавливать. Проверки 5.1 — детерминированные функции сервисного слоя, вызываемые в точках перехода, а не «движок правил»; код фактом подтверждает, что вторая попытка движка уже была и убрана (миграция 0013). Проверку шаблонов и документов по ГОСТ Р 21.101-2026 реализуем позже: сверка шаблонов — волна 1, проверки — волна 2.

**5.2. Внешние заключения и итерация согласования.** Заключения экспертизы, письма РСО (по техусловиям) и служб заказчика регистрируются как входящие документы с реквизитами (орган, дата, номер, вердикт: отказ или согласование с замечаниями). Пункты заключения разносятся в замечания вручную, каждое со ссылкой на пункт (лист, пункт, цитата); у заключения — чек-лист комплектности разбора, пока не закрыт, заключение числится необработанным в сводке ГИПа. Единица модели — итерация согласования: пакет замечаний заключения → ответы и исправления → новое заключение; внешнее замечание закрывается только официальным документом органа, конечное положительное заключение закрывает итерацию (решение владельца: экспертиза выдаёт положительное заключение только после снятия всех замечаний). Для РСО и служб заказчика запасной исход — официальное письмо-ответ. Вердикт заключения определяет блокируемость его замечаний — внешний блокирующий флаг вручную не ставится. Возможный исход замечания РСО — «породило новую версию исходных данных» (связь с правилом причин версий). Реестр ответов согласующему — генерируемый документ-снимок. Аудит: сущности нет — точка опоры нулевая; рудименты, которые нельзя терять при проектировании: Issue.project_organization/department — строки органа/отдела (issues/models.py:66-67), external_id и приём внешних замечаний через API sync_issues (issues/models.py:37-43; services.py:4789-4880). Замечания заключения порождаются с указанием органа — чтобы «внешний блокирующий флаг» (волна 0, п. 6) отличал внешние замечания от внутренних по данным, а не по договорённости на словах.

**5.3. Отчётные формы — зафиксированные снимки.** Данные правятся только в системе. Журнал регистрации изменений — живой реестр в системе; документ-снимок с фиксацией (кто, когда, по каким данным) создаётся только при официальной выгрузке. Возврат от экспертизы — импорт как новая ревизия через модель, не заменой файла. Аудит: все существующие выгрузки генерируются на лету и не фиксируются (vedomost.xlsx views.py:4821-4894; матрица xlsx/pdf views.py:2334-2670; реестр замечаний issues/views.py:469+). Готовый образец фиксации уже в коде — S3-outbox: schema_version, generated_at, generation, sha256 файлов в metadata.json (storage/domain/sync/export.py:59-129). Требование к снимкам 5.3: не ниже этого образца (кто запросил, когда, поколение данных, контрольные суммы).

**5.4. Разрешение на внесение изменений (форма 9).** Изменение документации, ранее переданной заказчику, — только через разрешение на внесение изменений по форме 9 приложения Л ГОСТ Р 21.101-2026: обозначение по журналу регистрации (нумерация по ГОСТ Р 21.1003), содержание изменения, код причины из таблицы Л.1. Внутренняя причина версии автоматически отображается в код Л.1 (например «устранение ошибки» — код 4). Переход «новая версия переданного документа» блокируется без утверждённого разрешения. К разрешению прикладывается декларативный список изменённых листов. Аудит: в коде замка нет — есть только запрет загрузки в ARCHIVE (services.py:3374-3379) и запрет обновления в PUBLISHED при открытых замечаниях (services.py:3453-3468); новая версия в PUBLISHED без замечаний загружается свободно. Опоры уже созданы в волне 0: признак «документ передан заказчику» (главное состояние документа — волна 0 п. 1) и ChangeSet со списком листов (волна 0 п. 8). Решение владельца: разрешение на внесение изменений остаётся в волне 2 — это одна процессная семья с внешними заключениями (5.2) и журналом регистрации изменений (5.3).

7.2.5 ГОСТ (учет версий и контроль доступа не заменяют РВИ).
Статусы РВИ: Черновик (редактируется, не влияет на действия)
и Утверждено (неизменяемо; опечатка — аннулирование выпуском
нового разрешения). Составление — ГИП. Утверждение — роль
«Руководитель» (новая системная роль, назначается владельцем
организации; права: утверждение РВИ, просмотр документов
организации, добавление замечаний к документам); если все
документы РВИ вне архива — утверждать может ГИП; если хотя бы
один документ в «Архиве» — утверждает только Руководитель
(строгое правило для общих РВИ). Точки срабатывания РВИ:
(1) повторная загрузка версии документа с охватом — сервис
требует утверждённое РВИ, связанное с документом, с нерасходо-
ванным изменением; версия хранит номер изменения и обозначение
РВИ (данные для таблицы изменений основной надписи и формы 10
приложения М); (2) вывод из архива (ARCHIVE -> WIP, выполняет
ГИП) — только при утверждённом РВИ, связанном с документом;
размещение при выводе не меняется (правило 1.9); (3) аннулиро-
вание документа — по утверждённому РВИ с записью «аннулировать»
по формуле ГОСТ. Обозначение РВИ (графа 1) генерирует реестр —
журнал регистрации разрешений по ГОСТ Р 21.1003-2009, сквозная
нумерация в рамках организации; вручную не вводится; формат
обозначения уточнить по ГОСТ Р 21.1003 при реализации. Связь
РВИ с документами — многие-ко-многим; на каждой связи: номер
изменения (графа 4) и список листов (графа 5, «Все» — при
замене/аннулировании всех листов). Графы 13–16 печатной формы
(согласования, нормоконтроль) заполняются из фактов нормоконт-
роля; отдельная вкладка «Нормоконтроль» — будущий этап, там же
вопрос участия ИИ. Печатная форма: форма 9 (первый лист) и 9а
(последующие), наименования граф — дословно по приложению К,
размеры — по оригиналу стандарта (стр. 48–49 приложения К);
экспорт в PDF. Подлинник РВИ хранится в СОД как ДЭ (7.2.1).

**W4-2 (реализовано):** коды причин — по таблице К.1 (1
«Введение усовершенствований», 2 «Изменение стандартов и норм»,
3 «Дополнительные требования заказчика», 4 «Устранение ошибок»,
5 «Другие причины»; пусто = прочерк). Номер изменения на связи
РВИ↔документ назначает система: следующий порядковый номер изменения
этого документа (номер per документ, не per РВИ). Расход изменения
фиксируется `applied_action` (версия / вывод из архива / аннулирование);
вывод из архива расходует изменение сразу, последующая загрузка версии
по тому же РВИ не требует повторного расхода. UI: отдельный раздел
`/rvi/` (список, карточка, создание, утверждение), без печатной формы и
аннулирования РВИ — они перенесены в W4-3.

**W4-3 (реализовано):** обозначение РВИ — «N-YY» (сквозной номер
журнала, две последние цифры года; допущение W4-1 исправлено). Печатная
форма 9/9а — A4 альбомная, дословные наименования граф, графы 1–8
28/45/52/11/14/88/10/29 мм, графы 13–16 — прочерки; экспорт PDF через
reportlab (как «Матрица заданий»). Графа 2 сокращает базовую часть со
второго документа («2345-12-АР; КЖ; ОВ»); содержание печатается по
каждому документу с подчёркнутым обозначением, документы разделены
линией, продолжение — на листах 9а. Даты подписей — две последние цифры
года. Аннулирование РВИ: черновик — ГИП-автор или Руководитель;
утверждённое — Руководитель либо ГИП, если все документы вне архива;
обозначение остаётся занятым в журнале, статус пишется в историю,
аннулированное РВИ только просматривается и не возвращается запросом
нерасходованного изменения. Форма 10 (прил. М) — таблица регистрации
изменений документа из версий, выпущенных по РВИ; листовые графы —
прочерк, пока в модели версии нет отдельных данных.

**W5-1 (реализовано):** подлинник РВИ — электронный документ архива организации (ГОСТ Р 21.101-2026 п. 7.2.3/7.2.5, ГОСТ Р 21.1003). Фиксируется в момент утверждения и в момент аннулирования; неизменяем после записи (insert-only). Формат файла — PDF (существующий рендер печати 9/9а). Хэш SHA-256 файла, инвентарный номер (сквозной по организации, формат «N-YY», реестр `ChangePermissionOriginalRegistry` с `select_for_update` на нумерации), время записи хранятся в `ChangePermissionOriginal` и дублируются в `ChangePermissionStatusLog` той же транзакцией. Constraint: не более одной записи каждого типа на РВИ. Точки записи (только две): `approve_change_permission` (после утверждения) и `annul_change_permission` (после аннулирования; пометка «АННУЛИРОВАНО» в графе «Примечание» печатной формы — отдельная графа ГОСТ не предусмотрена, выбран наименее инвазивный вариант). Повторная запись невозможна по модели W4-1; при попытке — явное `ValidationError`. Сервисный слой не предоставляет update/delete для подлинника; изменение файла/хэша после записи — исключение. Контроль целостности: `ChangePermissionOriginal.verify_sha256(data)` (минимум для будущего просмотра архива, без UI). Инвентарная книга — админ-панель (только чтение) и список подлинников в карточке РВИ через `related_name='originals'` (без загрузок/удалений); полный UI архива организации — следующая волна.
